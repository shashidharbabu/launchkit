RocketRide App Styles

Three presentation archetypes cover every app in the platform. All three share one page grammar: shell sidebar on the left, a page header (title + subtitle + actions), content below, status bar at the bottom. Only the middle zone changes per archetype. Everything is drawn with the real rocketride-default token values, and every rule is annotated with the token or commonStyles name an implementation should use. This page is the canonical visual guide for app UI work: it began as the approved mockups for the 2026-07 UI consistency program, and now reflects the design as shipped — including the decisions made during implementation and the hard-won learnings collected at the bottom. When code and this page disagree, treat this page as the intent and raise the conflict.

Which archetype does my app use?

Pick by what the app manages, not by taste. An app may combine them: a connection-oriented app shows Archetype C as its landing view, then opens documents per connection using Archetype B.

ArchetypeUse when the app...Apps
A — Dashboard Presents platform data and settings as navigable views; the sidebar is the only navigation; one view fills the client area. admin-ui, benchmark-ui, brandy-ui, monitor-ui, hello-ui
B — Document Opens one or more documents/sessions in tabs (DocTabs), each tab holding an editor or viewer, optionally with in-page view tabs. rocket-ui, aparavi-ui, explorer-ui; test-ui and profiler-ui once a session is open
C — Connection manager Connects to multiple sources; the landing view lists sources as cards, the sidebar lists them for quick switching. models-ui, profiler-ui and test-ui landing views

PageViewControl and SidebarMenu — one entry shape, two components

Superseded design note (2026-07-08): the original "ViewMenu with a placement flag, host renders it" model shipped and was then revised after live use. What replaced it is two independent stock components sharing one entry shape (ViewMenuEntry: id, label, optional count, optional error severity, optional icon): the PageViewControl — the page-tabs strip a view renders itself at the very top of its own content, in every host — and the SidebarMenu — a plain vertical menu list an app composes into its sidebar content, zero, one, or several per app. There is no placement flag and no publish/host machinery: the view owns its strip, the app owns its sidebar menus. Views still never hand-roll tab bars — consistency is enforced by the stock components, exactly as with Card or DataGrid.

Sidebar anatomy (shell-ui host)

If an app defines a sidebar, its content renders inside a shell-based sidebar frame: the shell always provides the Header at the top and the Footer at the bottom. The app supplies only the middle content — registered via useSidebarContent: SidebarMenu(s), Explorer, custom sections, in any order — and that middle region scrolls when the content is taller than the sidebar, while header and footer stay fixed. When the sidebar collapses to the icon rail the app content is still rendered with useSidebarCollapsed() reporting true; each component shows an icon form or nothing.

  • App content slot (scrolls) — everything between header and footer belongs to the app: stock components (SidebarMenu, Explorer) and custom sections in any order. When content exceeds the sidebar height, only this region scrolls; header and footer stay fixed.

Stock component library

The content of every tab or document is completely up to the app — exactly like the sidebar: the app decides which components to render and may draw free-form UI (pipeline canvases, chat, file viewers) wherever it needs. Consistency comes from the library, not from a forced layout: whenever a piece of UI matches a stock component's purpose, the app renders the stock component instead of drawing its own. Stock components are actual React components exported from shared-ui, not bare style definitions — commonStyles remains the styling layer they are built on, but apps mount components. The mocks below carry boundary chips marking ownership: Host chrome the shell/vscode owns it, apps never draw it — Stock a library component the app chose to mount — App content free-form region, entirely the app's. DocTabs Host chrome import { Documents, DocTabs, DocSplitLayout } from 'shell-ui'

The document tab strip at the top of the client area — one tab per open editor in an editor group, following the VS Code document model. Each tab shows the editor label, a modified-dot for unsaved documents, and a close glyph on hover; the active tab of the focused group carries the 2px --rr-brand underline. Tabs drag to reorder and drag between groups (split panes). Only tabbed (Archetype B) apps have it; dashboard apps have no tab strip at all.

Usage

import { Documents, DocTabs, DocSplitLayout } from 'shell-ui'; // The app owns the document model: one Documents instance over its VFS. // The shell never sees it — "host chrome" here means the strip is part of // the standard frame, not something a view may restyle or hand-roll. const docs = new Documents(vfs); // Anything that opens a document adds a tab (Explorer onOpenFile, deep links). docs.openDocument('ingest/analyze.pipe'); // Client area: DocSplitLayout renders the split tree; each pane renders its // own DocTabs strip bound to its editor group. <DocSplitLayout docs={docs} renderPane={(groupId) => ( <> <DocTabs docs={docs} groupId={groupId} isActive canClose={false} /> <PipelineEditor docs={docs} groupId={groupId} /> </> )} />

Props (DocTabsProps)

PropDirTypeDefaultDescription
docsINDocumentsrequiredThe app-owned document store to read state from and dispatch actions to.
groupIdINstringrequiredThe editor group whose tabs render in this strip.
isActiveINbooleanfalseWhether this group is the focused group (drives the brand underline).
canCloseINbooleanfalseWhether the whole group may be closed (false when it is the only group).

onSplitOUT(groupId, orientation) => void—Requests splitting this group horizontally or vertically (SplitOrientation).
onCloseGroupOUT(groupId) => void—Requests closing this entire group.

How it works

  • The document model is three layers: Document (one per URI; in-memory content, dirty flag, version counter), Editor (a view onto a document with its own viewport state), EditorGroup (a pane holding ordered editors). docs.useStore() subscribes React to changes.
  • docs.openDocument(uri) opens a VFS-backed document; docs.openStaticDocument(uri, label, content) opens non-file tabs (monitor views, webviews) that skip VFS read/write and never go dirty.
  • Drag-and-drop uses an editor-transfer MIME type (application/x-rr-editor); dropping on another strip moves the editor between groups.
  • Switching tabs unmounts the previous document's view and mounts the next — which is why per-view state like sidebar registration follows the active tab automatically (see Sidebar frame).

When to use it

  • Archetype B (document) apps: mount one Documents instance and let DocSplitLayout + DocTabs render the strip. Never draw a lookalike tab bar for documents.
  • For pages inside one document, use a PageViewControl — DocTabs is only for switching documents/sessions.

StatusBar Host chrome shell-ui internal — apps never mount it

The bottom bar of the shell with the global connection status: app name on the left (click toggles the bottom panel), a connection dot + label when authenticated, and the Ready / Offline state on the right. There is exactly one connection state for the whole shell — never per-app or per-tab, since one tab cannot be connected while another is not. In the VS Code host the equivalent is VS Code's own status-bar contribution, outside the webview.

How it works

  • Column management: drag a header edge to resize, drag a header to reorder, open the header menu (any column) to toggle column visibility or reset the layout. All of it persists when tableId is set. Columns opt out of the popup and its toggle list with rrNoPopup: true on their GridColumnDefinition (actions / icon columns; decision 2026-07-15 — replaced the old headerMenu: false marker, which @types/tabulator-tables cannot type).
  • LOCAL mode: a new data identity applies silently — scroll, page, and sort are preserved, so 2s poll loops are safe. The built-in bar searches the loaded rows client-side, and committed filters (header popups AND the strip) apply grid-internally with the server convention's semantics — onFiltersChange is an optional observation hook, not a requirement.
  • REMOTE mode: fetchPage receives { page (1-based), size, sort, filters, search? } and returns { rows, total }. A rejected promise keeps the prior rows on screen and shows a transient "Failed to load" overlay — stale data never silently looks healthy, and a flaky refresh never blanks the table.
  • The list-API convention (server side): every list endpoint accepts { page (1-based), page_size, search?, sort?: [{field, dir}], filters?: Record } and returns { rows, total, page, pageSize }. Filter values are a STRING (type-driven: strings contains, discrete codes exact, booleans coerced) or an ARRAY (set membership — IN (...); on JSON array columns: contains ANY element); datetime ranges via key__gte/key__lte (date-only upper bounds are end-of-day inclusive). list_distinct serves checklist values for any non-excluded column. Models declare only exceptions (__list_exclude__ etc. on the SQLAlchemy Base — see extension/src/extension/saas/db/list_query.py). Fetchers forward req.sort/req.filters/req.search verbatim.
  • Declared vs auto columns: THE model is the full declared contract — EVERY available column with its rrType, default-visible ones carrying rrDefault (array order = display order) and bespoke formatters, the rest unflagged (hidden by default; the shared autoFormatter heuristic covers their rare reveal). The declared defaults — layout, rrDefaultSort, rrGroup — are what the user sees whenever they have no persisted layout, and what Reset layout returns to. autoColumns remains for views that have not migrated: every undeclared row key becomes a hidden addable column, but auto columns carry no type, so they always filter as text. Toggle either kind from any column's header menu; visibility and width persist per user.
  • Filters (when declared) render as a strip the grid owns — uppercase labels, 30px controls, no Apply button. The typeahead type takes an async search(q) returning { value, label } options (store ids, display names); selects include their own "All ..." empty-value option. Prefer the type-driven header filters — Audit Logs dropped its strip for them (2026-07-15); the strip remains for filters that have no column (e.g. cross-field typeaheads).
  • Header filters (Excel-style, type-driven): every column's popup combines a filter control chosen by the column's rrType (text contains; distinct-value or Yes/No checklist sent as an ARRAY = IN; Start/End date range writing field__gte/field__lte) with the show/hide toggles and Reset layout — interpreted by the server on REMOTE grids and by the grid itself on LOCAL ones, with identical semantics. A brand dot on the header title marks an actively filtered column — a date column is active while EITHER bound is set, and its popup Clear empties both. Filter values are query state — they share the one filter record with the strip and are NOT persisted with layouts.
  • Format section (header popup, 2026-07-16): live display picks between the FILTER and COLUMNS sections — alignment buttons (MS-Office-style justification icons) on every column, plus a type row: 'date' columns get a date row [MM/YY] [MM/DD/YY] and a time row [HH:MM] [HH:MM:SS] [24HR] [UTC] (the pick pairs are each exclusive, composable to "date time"; [24HR] and [UTC] are independent toggles). Formatted datetimes render in the viewer's LOCAL time by default — the wire contract is UTC, and zone-less ISO strings are stamped UTC before parsing (JS would otherwise read them as local) — while [UTC] renders the UTC readout (including the date part: a UTC instant near midnight falls on a different local date); 'number' columns get exclusive decimals [.] [.0] [.00] [.000] plus independent [,] thousands and [$] currency toggles. Picks apply LIVE (no Apply step — display, not query), clicking the active pick clears it, and the map persists per user with the layout (Reset layout drops it; the title bar's Clear does not). Rendering falls back to the column's own formatter for unparseable values.
  • Title-bar search is collapsible (magnifier toggle, decision 2026-07-18): the field is COLLAPSED by default — the bar reads {title} {magnifier} {count} on one line — and the magnifier (a bare glyph styled like the gear: quiet secondary, primary on hover / while open) expands it in place with autofocus. Collapsing CLEARS the term, so a hidden field never hides an active search (the same visibility principle as the header-filter brand dots); Escape in the field clears a live term, and a second press collapses. The open state persists per user with the display settings (Reset layout restores the collapsed default; Clear leaves it alone). With search down to one glyph it stays enabled everywhere — noSearch is now exceptional; "the table is small" no longer justifies it.
  • Sorting: header clicks cycle Asc → Desc → None (tri-state); arrows render ONLY on actively sorted columns — a permanent gray arrow reads as "sorted" and lies. "None" sends an empty sort, and every list endpoint then falls back to its default order (newest-first for entity tables) with an unconditional PK tiebreak — paging is deterministic even across duplicate timestamps.
  • Column reveal sizing: a column shown from the popup content-fits its width (header + loaded cells, clamped at 480px so a fat JSON payload cannot blow the layout); drag wider from there. JSON cells ellipsize at the CELL edge — widening the column reveals more text. Changing a FORMAT pick never resizes columns (cells reformat in place).
  • Timezones: the wire contract is UTC — the server pins every DB session to +00:00, and the grid stamps zone-less ISO strings as UTC before parsing (JS would silently read them as local). Formatted datetimes display in the viewer's LOCAL time by default; the [UTC] pick shows the UTC readout.
  • Footer renders only when the set spans more than one page (total > pageSize) — filtered or not (decision 2026-07-08, carried over).
  • Actions columns are RETIRED (record-panel standard, 2026-07-17): grids are pure data — row click opens the record panel and every verb lives in its footer, which frees row width, removes the pseudo-column from exports, and gives users one rule ("click the row; everything you can do to it is in the panel"). createActionsColumn remains only for legacy grids not yet migrated; do not add it to new views.
  • Cells are DOM, not React: formatters return elements. The .rr-cell-* classes in the grid theme replicate StatusBadge / Button values from the same --rr-* tokens, so themes stay in sync; a deliberate shape redesign of those components must be mirrored there.
  • Composition: the grid draws no outer border. Full-page grids sit directly in the content area under the page header. Card-hosted grids are CardDataGrid inside a HEADERLESS Card with noBodyPadding — never give that Card a header (the grid's header IS the card header), and reserve the Card toolbar slot for controls the grid does not own. Reference implementation: shared-ui/modules/billing/CreditsPanel.tsx (data state = headerless Card + CardDataGrid; empty state = classic Card header, since there is no grid to own it).

DetailPanel Stock — shared-ui import { DetailPanel } from 'shared'

The right slide-over drawer — and since 2026-07-17 THE RECORD PANEL: the single surface for INSPECTING, EDITING, and CREATING a record. Row click opens the record; "+ New X" (a CardDataGrid actions button) opens the SAME panel empty. Grids consequently carry no Actions columns — they are pure data. Composes from the shared vocabulary: a fixed EntityHeader (42px avatar slot + 17px/700 title + secondary line + close), an optional underline tab strip (ViewMenuEntry shape), an independently scrolling body of Sections (or a form in create/edit mode), and the footer. The full interaction contract below (2026-07-18) is THE RULEBOOK for every record panel — refactors are measured against it clause by clause.

The interaction standard (2026-07-18) — modes

One invariant answers "does this commit now?": the panel is always in exactly ONE mode, and the MODE — never the particular panel — decides. A panel is a PanelState union (closed / inspect / edit / create / present); it owns its form state, validation, saving flag, and error state locally, and receives RAW async host actions (onCreateX, onRevokeX) — never modal-opener callbacks.

  • Inspect — read-only facts plus VERBS. No editable inputs anywhere: chip collections render read-only (no ×, no + Add). Every mutation is a button that commits immediately, ConfirmDialog-guarded when destructive or hard to reverse.
  • Edit — entered ONLY via the footer [Edit]. Editable fields become inputs; everything is STAGED — nothing commits until Save. Save returns to Inspect with the panel open; Cancel discards back to Inspect.
  • Create — the same staging rules, opened empty by "+ New X".
  • Present — a one-shot result display (the ApiKeys secret reveal); single [Done], which exits the panel (peels, in a stack).

The footer contract

Inspect (editable record): [Delete] [Send Email] .................. [Edit] Edit, clean: [Delete] [Send Email] .................. [Cancel] Edit, dirty: [Delete] [Send Email] ........... [Save] [Cancel] Create, empty: .................. [Cancel] Create, dirty: ...... [Create X] [Cancel] Present: .................. [Done] Pure inspect: NO FOOTER — the header X / Escape close
  • The footer is RECORD machinery; the header is STACK machinery. Save/Cancel/Edit and record-level verbs live in the footer and act only on this panel's record; back and X live in the header and do navigation. A footer verb NEVER navigates.
  • Left cluster: record-level actions — verbs about the record as a whole ([Delete], [Send Email], [Export]) — left-anchored via marginRight: 'auto', destructive ones LEFTMOST (maximum distance from Save/Cancel), danger-styled, ConfirmDialog-guarded.
  • Right cluster: mode machinery. [Save] MATERIALIZES on the first change, to the LEFT of the stationary [Cancel] — Save's presence IS the dirty indicator, and Cancel never moves out from under the pointer. [Create X] follows the same appears-on-dirty rule (an empty create form has nothing to submit; the first keystroke reveals it).
  • Footer presence signals editability: a pure-inspect panel has no footer at all (Connections, Tasks, Audit entries, Transactions).
  • Capability-gated verbs are HIDDEN, not disabled (no [Edit] without permission); disabled is reserved for in-flight operations.

Fields vs verbs — the razor

  • If it changes what the record IS → it is a FIELD → staged behind Save. System permissions are fields: read-only chips in Inspect, editable in Edit, one commit, one audit event.
  • If it DOES something to or with the record → it is a VERB → immediate, ConfirmDialog when destructive or consequential (enable/disable, revoke, resend invite). Verbs never flip the mode and stay live even during Edit — they are independent of the staged fields.
  • Fact-level verbs sit in the BODY next to their fact (Status: Enabled → [Disable User] on the same row); record-level verbs sit in the footer's left cluster.

Save, Cancel, dirty, and failure

  • Save commits every staged field at once, returns to Inspect, and the panel STAYS OPEN — live re-resolution flips the badges. A failed save stays in Edit with the staged values intact and shows the error.
  • Cancel discards staged fields and returns to Inspect — a MODE exit, never navigation.
  • The dirty guard: Cancel, X, Escape, or back on a DIRTY form all raise one stock ConfirmDialog ("Discard changes?" — destructive [Discard] / [Keep Editing]). A clean form exits instantly. Silent discard is banned.
  • In-flight: footer verbs disable, the primary swaps its label ("Saving..."), and the panel cannot be dismissed until the call resolves.
  • Errors render INSIDE the panel as a stock Banner variant="error" at the top of the body (of the panel that owns the action). Page-level Banners are for grid/list failures only.
  • After create: flip to Inspect of the new record when the host can resolve it from the refreshed rows; close otherwise. A one-time secret flows to Present instead.
  • After delete: the record ceased to exist — the panel peels (stacked) or closes (root).
  • Tab switching while dirty is ALLOWED — staged edits are record state, tabs are views; nothing discards except explicit Cancel or a confirmed discard.
  • Concurrent server-side changes during Edit (decision 2026-07-18): staged fields NEVER re-seed mid-edit — the user's typing is sacred — and Save is last-write-wins, no version check. Inspect-mode facts and body verbs keep live-resolving as usual. (A non-blocking "this record changed while you were editing" warning Banner is a permitted future enhancement; silent field clobbering is not.)
  • data-rr-autofocus on the first input of every form mode.

Exits — X, Escape, back, sliver

  • X closes the ENTIRE stack. If ANY layer holds a dirty form, ONE aggregate discard confirm covers the exit; layers unwind in order and focus restores to whatever opened the root.
  • Escape peels the innermost layer of STATE: open ConfirmDialog → Edit mode (acts as Cancel, dirty-guarded) → panel (peel) — one keystroke can never blow past unsaved work or out of a stack.
  • Back arrow (depth ≥ 1 only) sits LEFT of the avatar in the EntityHeader, aria-label / tooltip "Back to {parent title}"; peels one panel with the dirty guard. The root panel has no arrow.
  • Clicking the parent's exposed SLIVER also peels (secondary gesture, same guard). The dim backdrop stays inert — it never closes anything.

Scroll regions

  • The body scrolls independently between the ALWAYS-VISIBLE header and footer — built into the component. Consumers never wrap the body in their own overflow container.
  • Tabs own their scrolling: when tabs are declared the body stops scrolling (flex column) and each tab panel manages its own overflow — simple Section stacks wrap in the stock PanelTabBody; a tab hosting a grid or viewer lets that content own it.
  • List tabs are LOCAL-mode title-less DataGrids — the grid standard ("every tabular list, no exceptions") applies inside panels too; no hand-rolled tables. A list tab's row click pushes a child panel.

Stacked panels (2026-07-18)

  • A child record (an API key inside a user, a member inside an org) opens by PUSHING a second DetailPanel over the first; "+ New X" inside a tab pushes a child in Create mode. Depth cap: TWO stacked panels — a third level means the middle record has outgrown a drawer and deserves its own page.
  • Width model: the TOP panel's width W is the stack's one value; each panel below renders at W + 40px per level, so the root is widest and every exposed sliver is exactly 40px. Dragging the top panel's handle resizes the WHOLE stack; lower panels' handles disable; the top clamps to the viewport minus 40px per level below it. A STACK's width is session-local; a LONE panel should opt into persistence (see "Remembering width").
  • Lower panels are INERT except the sliver's peel click, with an extra dim layer between levels so depth reads at a glance.
  • Parent state survives the push: mode, staged edits, active tab, scroll position — the parent never unmounts. Drilling down is non-destructive and needs no guard; child mutations reach the parent through live resolution (revoke the key in the child, the parent's list shows Expired).
  • Footers are PER-PANEL and act only on their own record — Save/Cancel on a child never navigates the stack. ConfirmDialog / stock Modal stack above ALL panels; peeling restores focus to the panel below.
  • contained panels (Account dialog) stack by the same rules inside the dialog's bounds.

Remembering width (opt-in persistence, 2026-07-19)

A resizable drawer defaults to SESSION-LOCAL width — it reopens at its width/height every time. Every resizable panel SHOULD remember the size the user dragged it to, via the opt-in persistKey + persistence pair. Pass a stable key and an adapter and the drawer restores its saved size on open (re-clamped to the current viewport band) and saves on every resize-end.

  • Store in the user's WORKSPACE data, never localStorage — every app has a shell-managed per-app preferences store (rocketride.<app>.workspace.json), so a persisted width survives per-user and syncs like every other preference. localStorage is per-device and invisible to the workspace; it is banned for this.
  • Wiring — the adapter is just { read(key)=>number|undefined, write(key,value) } over whatever prefs API the host exposes:
    • Canvas panels: FlowPreferencesContext — getPreference / setPreference.
    • Other apps: the shell's useWorkspace() — prefs[key] / updatePrefs({ [key]: value }).
  • Key naming: one stable key per panel role, not per record — e.g. panelDetailAddNodeWidth, panelDetailConfigWidth. A record-varying title is NOT a key.
  • Only a LONE panel persists; a stack's shared width stays session-local. Reset (double-click / Home) is remembered too — the panel reopens at its default, not the last dragged size.

Record resolution

  • Live resolution: resolve the record from props by id on every render, so a server refresh updates the open panel in place. Keep the last-known snapshot when the row pages out of the current page; auto-close only when the user's OWN delete removed the record.
  • Immutable event records (audit entries, transactions) may hold a whole-row snapshot instead — they cannot change, so live resolution buys nothing.
  • Multi-step in place: a create flow that returns a one-time secret flips the SAME panel to Present (see ApiKeysPanel) — no second dialog.
  • Avatar in the EntityHeader for identity-bearing records (users, teams, keys); none for event records.

How it works

  • First-field focus is the panel's job, never native autoFocus: mark the opening input with data-rr-autofocus and the drawer focuses it (with preventScroll) after the slide completes. Native autoFocus fires at mount — while the drawer is still translated off-screen — and scroll-chases the input, visibly dragging the page (the "page flies in" bug, 2026-07-17).

Overlay z-index 1500; stock Modal / ConfirmDialog sit at 2000, so flow dialogs and confirmations stack ABOVE every open panel, and the shared overlay-layer registry makes Escape peel ONE layer at a time (confirm → edit mode → panel → panel → host dialog). Hand-rolled dialogs are banned for exactly this reason — the last two (UpgradeModal, TopUpModal) pinned their own z-index below the panel and rendered underneath it until converted.

The centralised connection singleton. programshell-api freeze covers everything; the contract is permanent once publishedThe versioned shell contract covers the ENTIRE shell-ui export surface, generated only by ./builder shell:freeze; a breaking change must fail the shell compile. Mechanism (rebuilt 2026-07-09): each freeze APPENDS a self-contained snapshot versions/vN.d.ts (never rewrites or drops an existing one). Enforcement is a set of per-version floors in shell-ui's contract-check.generated.ts plus a hand-written anchor in contract-hold.ts: the live surface is asserted to still satisfy EACH frozen version separately (current ⊇ v0, ⊇ v1, …). It is deliberately NOT an intersection type — intersecting the snapshots collapses nominal members (enums like ConnectionState) to never. Removing or breaking anything ever frozen fails shell-ui's OWN tsc/build at those floors, and freezing only ever appends, so there is no shell:freeze path to resolve it. This REPLACED the earlier generated compat-gate + snapshot-diff design, whose escape hatch let a version-history reset happen once (2026-07-08). The freeze is fully automated except the hand-curation of api.ts (add a name to the shellApi object or an export type): it writes the version file, the barrels, the floors, and the version constant (src/apiver.ts) itself. App registration stamps each app's apps.json with shellApiVersion (read from apiver.ts), so the lowest version in use across apps is known — the safe floor for PRUNING obsolete frozen versions. Dropping a member requires hand-deleting a "FROZEN — do not edit" version file (a deliberate, review-visible act; optionally CI-guarded), and is only safe once no app depends on that version. After publication, an export, once frozen, can never be deleted or broken — the only paths are additive change and deprecation (keep it working, mark it @deprecated). Treat any proposed removal from shell-ui's exports as a contract event requiring design-owner sign-off.

Implementation learnings

Hard-won during the program — each of these cost real debugging time. Read before building or reviewing app UI; add new entries when the next lesson lands.

  • Never mix a border shorthand with a conditional border longhand in React inline styles. React's style diffing does not expand shorthands: layering borderColor over a border: shorthand only in one state leaves the stale color behind when the state flips (the "stuck outline" bug — selected sidebar rows kept their outline after deselection). Emit borderWidth/borderStyle/borderColor longhands in BOTH branches so the property set never changes across renders.
  • Give selectable rows a constant transparent border (border: 1px solid transparent when inactive) so toggling selection never changes row height — no sibling reflow on select.
  • key={id} whenever the same component type renders different logical instances (detail views switched by an id prop, viewers per file). Without it React reuses state across instances.
  • Registration hooks use a two-context split (stable API context for the registrant, resolved state context for the reader) so content updates never re-render the registering app, plus a per-hook ownership token with last-writer-wins so mount/unmount order during a switch is irrelevant. Register in useLayoutEffect (pre-paint), not useEffect, or the chrome flickers one frame behind.
  • Polling: usePolling is shell-connection-gated by default. An app polling its OWN connection (models-ui GPU telemetry) must pass {gate: 'none'} — the symptom of the default is polling that silently stops when the shell disconnects. Never hand-roll setInterval loops.
  • fetchPage speaks camelCase and is 1-based; the server speaks snake_case (req.size vs page_size; req.page maps straight onto the 1-based list_* APIs with no offset math). The mapping belongs in the view's fetchPage, never in DataGrid. The symptom of a missed mapping is pagination that returns the same page forever.
  • Never vary the React className prop on Tabulator's container — Tabulator stamps its own classes onto that element at build, and a React className change REWRITES the whole class attribute, wiping them: the entire grid unstyles instantly (headers collapse to bare text, footers to inline links). State-dependent classes (the gear's grid-lines/zebra settings) must apply via classList.toggle in an effect, which preserves foreign classes; the className prop must be a constant.
  • Tabulator's setMaxHeight/setHeight are NOT no-op-safe — each call re-initializes the row renderer and forces a full redraw, and doing that at mount (even to "clear" a value that was never set: setMaxHeight('')) broke headers and pagination footers on every grid platform-wide. Call them only on REAL transitions, tracked with an applied-ref that resets per rebuild.
  • TypeScript does NOT excess-property-check literals returned through useMemo<T[]>(() => [...]) — the array literal loses freshness through the generic return position, so a typo'd or stale rr* column marker compiles silently and is simply IGNORED at runtime (proven empirically: a bogus property errors on direct assignment but passes through the useMemo shape; 89 stale markers once built "clean" this way). When renaming a contract marker, grep the callers — tsc will not find them. For new code prefer useMemo(() => [...] satisfies GridColumnDefinition[], []), which restores the check.
  • Elements inside display:none panels measure 0×0. Anything that measures itself (charts, canvases) must guard with a visibility check or defer measuring until shown.
  • Iframe theming goes in via srcdoc (inject the theme CSS into the HTML before load), not postMessage round-trips; keep the iframe visibility: hidden until its view:ready fires to kill the white flash.
  • Module Federation: shared-ui flows through the 'shared' singleton. Never re-export shared-ui symbols from shell-ui — two copies of one type is the duplicate-symbol trap that breaks assignability across the app boundary.
  • vscode webviews are isolated browser contexts. React context cannot cross them; anything shared must render inside the webview's own tree. Bridging requires a webview → extension host → webview postMessage relay — avoid designs that need it (this constraint helped drive the view-rendered PageViewControl).
  • Shell overlay dialogs render outside the client area's providers. Any host-coupled behavior must be checked in ALL embeddings: shell client area, overlay dialogs, vscode webviews, and provider-less standalone use.
  • Verify removals with grep gates. After retiring an API, grep both repos for every removed symbol (zero hits outside frozen contract history) — MF loads at runtime, so a missed consumer compiles fine and breaks in the browser.
  • Builder footgun: some register steps write env values back into the source-tracked .config. After any build, git diff the submodule's .config and restore it before committing — no real secret may ever land in it (the committed RR_SIGNING_KEY=<development> placeholder is deliberate and is not a secret).
  • Type casts are a smell; x as unknown as T is near-forbidden. A cast that seems necessary usually marks a type that should be fixed at its source (the SDK typing gap is tracked work, not a license to cast).
